# Notification dispatch immediately after a Worker deployment

Status: incident analysis and implemented mitigation, 2026-09-26. The explanation below is a **strong inference, not a confirmed edge trace**. The note itself did not send mail; the current Worker/CI implementation adds a capability gate and bounded retry, as described below.

## Observed sequence and discriminating evidence

GitHub Actions [run 36177202232](https://github.com/kleedaisuki/kleedaisuki.github.io/actions/runs/36177202232) applied remote D1 migration `0002_campaign_text.sql` at 19:06:37 UTC, then Wrangler reported Worker version `97465d03-103a-4b11-beb7-ea416a944410` deployed at 19:06:48.500. The next step began at 19:06:48.608 and its POST to the `workers.dev` URL returned HTTP 400 at 19:06:48.849. The new `atelier-fragment-v1` payload was accepted by a local Wrangler Worker, while the remote draft remained the earlier full-document snapshot (`html` length 822, `text IS NULL`). This was a draft with `send:false`; no new deliveries were created.

The previous Worker accepted `NotifyInput {id,subject,html,send}`. Serde ignores the new `format` and `text` JSON fields unless unknown fields are explicitly denied. Its legacy validator then requires `{{unsubscribe_url}}` in the raw `html`. The new fragment deliberately does not include that placeholder because the new Worker inserts it in the shell. Thus the **previous code deterministically returns `400 Invalid campaign` for this exact payload**. A request arriving about 0.1–0.3 seconds after the deploy completed is consistent with a transient version skew at the serving edge. Cloudflare documents that `wrangler deploy` targets 100% of traffic, but also states a newly changed version can take a couple of seconds to become available globally for version overrides; the latter supports a narrow propagation-window hypothesis, not proof that this POST ran old code ([versions/deployments](https://developers.cloudflare.com/workers/versions-and-deployments/), [version overrides](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/)).

Competing causes remain possible: CI could have posted to an older deployment URL or a different account/route; the deployed bundle could differ from the locally tested binary; or the new validator could have rejected CI's exact byte sequence. The CI log confirms the `ATELIER_WORKER_URL` was `https://atelier-moesegfault.moesegfault.workers.dev/`, matching Wrangler's printed deployment URL, reducing but not eliminating routing/configuration concerns. A 400 before persistence rules out a queued-campaign 409 and makes a D1 schema failure unlikely. The generic 400 body and missing invoked-version ID prevent conclusive attribution.

## Implemented small fix and remaining limits

1. Keep migration → deploy → dispatch ordering. Do not modify historical `send:true` campaign assets, replay all manifests, or manually send to subscribers as a test.
2. `GET /api/health` now exposes non-secret `mail_formats:["document","atelier-fragment-v1"]` while preserving its existing fields; it does **not** expose a source revision or invoked version ID. After deploy, CI polls the **same `workers.dev` origin** for `atelier-fragment-v1` support, at a fixed 2-second interval for at most 10 probes (each request times out after 5 seconds), before dispatch. An older Worker's HTTP 200 health response lacks the marker and is not treated as ready. Cloudflare's [version metadata binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/version-metadata/) remains an optional future diagnostic, not part of this implementation.
3. A health poll is not a transaction with the next POST, so it does not by itself exclude cross-edge or gradual-rollout skew. The implemented dispatcher makes at most **five** attempts of the **identical** `atelier-fragment-v1` POST at a fixed 2-second interval on an explicit HTTP 400, whether `send:false` or `send:true`, and does not retry network errors, 5xx, or 409. This is safe under the **current Worker contract**: both the old Worker's fragment-triggered 400 and all 400 branches in the new `notify` function occur **before** `upsert_draft` and `enqueue`; after persistence, a changed queued payload is 409. A true validation defect may therefore incur a short delay before CI fails, but cannot be hidden indefinitely. Do not generalize this reasoning to other endpoints or future Worker revisions without rechecking where their 400 responses occur.
4. For any future `send:true` manifest, keep the stable campaign ID and existing D1 immutability/idempotency contract. An identical replay against the new Worker must not enqueue additional deliveries; changed queued content must still return 409. On a timeout or ambiguous network failure, query `/api/admin/status?id=...` and reconcile before any replay; the dispatcher intentionally does **not** auto-retry these outcomes. The dispatcher currently logs the **HTTP status only** for a failed POST, not `cf-ray`, a validation error code, or an invoked Worker revision/version. Those could improve future diagnosis if implemented safely; never log bearer tokens, message HTML, or recipient addresses. `send:false` remains the default for visual QA and rollout checks.

An even stronger release gate is to deploy code in one workflow run and dispatch content in a later run, but it adds operational ceremony and still requires diagnostics/idempotency. A fixed sleep alone is cheap but cannot distinguish propagation delay from a malformed payload, so prefer the bounded capability gate. Cloudflare's [gradual deployment documentation](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/) explicitly discusses version-skew errors when two versions serve concurrently; no gradual split was configured here, so that page is a design warning rather than direct evidence for this incident.

## Falsifier / next observation

If the exact same new-format `send:false` payload still returns 400 when `/api/health` on the same origin consistently reports the new **capability**, inspect the invoked version ID through separate platform diagnostics and consider returning a specific non-sensitive validation error code (`invalid_format`, `invalid_html`, `invalid_text`). That would materially weaken the propagation hypothesis and point to an actual build or input mismatch. A successful identical retry with the new marker and one updated D1 draft row (still zero deliveries) would support, but not prove, transient version skew.
