The published site before migration used Astro static HTML, `zh`/`en` routes, a warm light palette (`#fff6ea`, `#4b2a1e`, `#e66a3f`) and dark palette (`#21130f`, `#f6e7dc`, `#f27a50`), a two-column desktop homepage that stacks on mobile, and crawlable content without JavaScript. These expectations were taken from the existing site CSS, markup, and public route contracts, not inferred from the new Worker code. The regression test is `tests/e2e/migration-contract.spec.ts`.

Local environment: Windows PowerShell, Node 26.8.2, pnpm 11.17.0 via `corepack.cmd`, Playwright 1.62.1, Wrangler 4.140.0. The globally installed `pnpm.ps1` shim is broken on this host; a repository-local `.temp/pnpm.cmd` wrapper for `corepack.cmd pnpm` was used so Playwright's preview server could start. Test and Wrangler state stayed under `.temp/` and `.cache/`.

## Owned-mailbox consent and notification attempt

The user supplied an owner-controlled Outlook test mailbox; its address is intentionally omitted from this public repository. A canonical-host `POST /api/subscribe` returned 202; a remote D1 read showed `pending`. After the user used the confirmation link, D1 showed `confirmed`. This demonstrates the live consent transition with that mailbox; it does not separately inspect Outlook's message metadata or prove the flow for arbitrary non-verified recipients. The owner found the original confirmation page visually poor, prompting the action-page redesign in deploy Action 36135578884.

The new `atelier-worker-launch-2026-09-25` campaign contained editable HTML and `send:true`. CI accepted it; remote D1 first showed one queued recipient. At `sent_at=1790340059285` (2026-09-25 12:40:59.285 UTC), the campaign was `complete` and its sole delivery was `sent`, `attempts=1`, with no recorded error. The owner confirmed that the message arrived in **Outlook's spam folder** and that its HTML layout and visible unsubscribe link displayed normally. This establishes the scheduled dispatch path, a successful Cloudflare Email Sending binding call, and actual receipt for **this Cloudflare-verified mailbox**. It does **not** establish inbox placement, the delivered plain-text part or one-click headers, Workers Paid entitlement, or delivery to arbitrary subscriber addresses. No unsubscribe POST was exercised. Cloudflare [notes that new domains can have weaker reputation](https://developers.cloudflare.com/email-service/reference/troubleshooting/); without message authentication results or comparative sends, that is a plausible explanation for spam placement, not an established sole cause.

## Cloudflare-unverified school-destination confirmation test (2026-09-26)

The owner supplied a school mailbox that was **not** among this Cloudflare account's Email Routing verified destinations. Its full address and the message ID are deliberately omitted from this public record. A pre-test exact-address D1 lookup found no subscriber row. A canonical Rust Worker `POST /api/subscribe` returned **202** and created one `pending` row. The owner reported that the confirmation message reached the school's **inbox**; the owner did **not** click its confirmation link. Recipient-side HTML rendering, text alternative, and headers were not inspected.

Independently, Cloudflare's GraphQL `emailSendingAdaptive` event dataset contained exactly one matching outbound event at **2026-09-25T18:35:35Z**, with `status=delivered` and no error. Cloudflare says this status means the recipient mail server accepted the message; it does **not** by itself prove inbox placement ([Email logs](https://developers.cloudflare.com/email-service/observability/logs/), [Email lifecycle](https://developers.cloudflare.com/email-service/concepts/email-lifecycle/), [GraphQL dataset](https://developers.cloudflare.com/email-service/observability/metrics-analytics/)). The owner's separate inbox report supplies that narrower observation for this one mailbox. Because the address was unverified in Cloudflare Email Routing, this is evidence of successful ordinary unverified-recipient sending for **one domain/address**, unlike the earlier verified Outlook test. Cloudflare's [pricing documentation](https://developers.cloudflare.com/email-service/platform/pricing/) says arbitrary recipients require Workers Paid, but the account's Billing UI plan status was not inspected; do not infer its recorded plan solely from this functional test.

An independent read-only Email Sending limits check after this test showed `usage.sent=1` of `quota=1000/day`; the earlier verified-destination test had shown `usage.sent=0`. That direction is consistent with Cloudflare's [pricing rule](https://developers.cloudflare.com/email-service/platform/pricing/) that verified-destination sends do not count toward quota while accepted ordinary sends do. It corroborates the classification of this test as a quota-counted send, but is not a substitute for inspecting Billing UI plan state or for testing other recipient domains.

After the test, an exact-address conditional deletion removed only that `pending` subscriber row (`changes=1`). A subsequent D1 check found zero school-address rows while the pre-existing confirmed Outlook subscriber remained. No second email, confirmation POST, update campaign, or unsubscribe action was performed for the school address. This cleanup matters: the test address is not left eligible for a later campaign without the owner's confirmation.

## Issues and boundaries

- Wrangler 4.130.0 initially could not start a Worker configured with compatibility date `2026-09-25` because its bundled workerd supported only through `2026-09-15`. Upgrading the pinned Wrangler/workerd dependency to 4.140.0 resolved this; no date override was needed in the passing run.
- The existing PDF.js client build emits a chunk-size warning (`PdfReader` about 607 kB before gzip), but the interactive reader is a lazy enhancement, not a dependency of initial HTML. This is a performance watch item, not a failed regression here.
- One owned-mailbox subscription, confirmation, and scheduled HTML delivery to Outlook spam are observed. A different Cloudflare-unverified school address received one confirmation in its inbox, backed by one provider `delivered` event; it was not confirmed or sent an update. Production unsubscribe POST, received plain-text and one-click headers, general cross-domain deliverability/inbox placement, and Billing UI plan/quota still require evidence. A `sent` D1 row alone records the Worker's successful provider-binding call; provider delivery events and owner receipt reports provide stronger but address-scoped evidence. Canonical-domain smoke does not prove globally completed DNS propagation.

Verdict: **CI deployment, DNS proxy cutover, local compatibility, preview/canonical reading and search routes, one scheduled HTML update received in Outlook spam, and one confirmation received in an unverified school recipient's inbox are verified. Broad deliverability/inbox rates, Billing UI paid-plan status, production unsubscribe POST, and global DNS propagation remain unverified**.
