# Atelier mailroom: one editorial identity across subscription touchpoints

Status: product/design specification, 2026-09-26. This describes intended behavior, not a claim that the current mail templates already meet it. Scope: the home-page subscribe section, confirmation email, editable publication-update email, and confirmation/unsubscribe action pages. Preserve the public site's established layout and theme, existing URLs and token/consent semantics, and already-sent messages. Do not resend the launch campaign merely to restyle it.

## Problem, evidence, and decision

The subscriber's journey currently changes visual and editorial language at each step. The subscribe section promises a message from `atelier@moesegfault.dev` when a new article or work appears. The action pages already use an `A/ Atelier` mark, warm paper/ink/vermilion palette, `ATELIER / MAILROOM` kicker, bilingual labels, and a publication-like footer. But confirmation mail is three bare paragraphs and a plain link. `notifications/atelier-update.html` uses unrelated gray/brown colors and generic placeholder copy; the launch update uses closer colors but a different structure and voice. Those are repository observations, not an inference about how a specific recipient's mail client rendered them. The school-mailbox test establishes inbox receipt of one confirmation, not visual quality or broad deliverability ([mail architecture](cloudflare-worker-mail-architecture.md)).

**Decision:** make the email and action-page journey read as one small editorial publication, not as four identical web pages. Keep the existing site and action-page composition; derive a compact *email-safe* expression of its identity. Confirmation is a brief transactional invitation. Updates are specific editorial notices about a published article or work, with one clear reading destination. Neither should feel like a systems-status broadcast or a marketing campaign. The `bounces@cf-bounce.moesegfault.dev` transport identity is not a design token or author signature; visual copy must not imply that visible `From`, envelope sender, and return path are identical.

| Touchpoint | Primary task | One visual/voice contract |
| --- | --- | --- |
| Home subscribe section | Understand the promise and request mail | Existing card and controls remain; name the publication as **Atelier updates / 工坊更新** and say confirmation may be needed. |
| Confirmation email | Decide whether to activate | `A/ Atelier` → small `MAILROOM / 邮件室` eyebrow → localized title and one-sentence reason → **Confirm subscription / 确认订阅** primary link → expiry/ignore note → publication footer. No claim that opening or GET activates consent. |
| Action page | Review and POST consent or unsubscribe | Existing page hierarchy remains. Its title, short English companion line, action verb, and return links use the same terminology as the mail. Success/error states keep the same shell and clearly say what happened. |
| Publication update | Understand what is new and open it | Brand/eyebrow → *actual content title* → concise editorial summary → one primary **Read the article / 阅读文章** or **View the work / 查看作品** CTA → optional secondary context → subscription reason and unsubscribe footer. Direct canonical content link, not a generic home-page CTA. |

## Visual system for mail

Email clients are not browsers. These are **literal hex values in the email**, mapped to existing `src/styles/global.css` tokens; do not import site CSS, rely on CSS variables, custom fonts, gradient, `color-mix()`, background images, animation, or script. A plain text wordmark is preferable to an image that may be blocked.

| Role | Email value | Site origin / usage |
| --- | --- | --- |
| Outer paper | `#fff6ea` | `--bg-color`; full-canvas fallback. |
| Inner paper/card | `#fffdf8` | `--surface-strong`; one centered reading column, up to 600 px. |
| Main ink / heading | `#4b2a1e` / `#26110b` | `--text-color` / `--heading-color`. |
| Secondary copy | `#805648` | `--text-soft`; still readable on inner paper. |
| Accent rule | `#e66a3f` | `--accent-color`; decoration, not small text on white. |
| Interactive fill | `#bd4525` with `#fffaf2` text | `--accent-strong` / `--on-accent`; approximately 5.0:1 contrast. |
| Text link | `#ad3d1d` on `#fffdf8` | `--accent-text`; underlined or otherwise unmistakable as a link. |
| Border | `#f3bf98` | `--border-color`; never the only state indicator. |

Use generous but bounded spacing: outer padding about 16 px on narrow screens and 24–32 px on wide screens; inner card padding about 24 px; 16 px body type at ~1.6 line height; 24–28 px headline at ~1.25; 12–13 px small uppercase/monospaced-looking eyebrow; 13–14 px footer. Use a system sans stack including Chinese platform fallbacks (`Arial`, `PingFang SC`, `Microsoft YaHei`, sans-serif); a Georgia-like serif may accent the brand/headline but must gracefully fall back for CJK. Avoid faux magazine ornament, emoji, and decorative imagery. One slim vermilion top rule, subtle border, plain `A/ Atelier` wordmark, and the repeated eyebrow are enough. The CTA is a real `<a href>` with visible verb and a filled background; it must remain an understandable text link when styling is stripped. Do not hide the raw destination: a separate visible URL or text alternative may aid clients that suppress styled links.

Mail should be single-column and readable at 320 CSS px without horizontal scroll. Use semantic source order and email-compatible layout (a small presentation table is acceptable), inline essential styles, explicit background **and** foreground colors, and a visible text fallback if CSS/media queries/images are suppressed. `@media` may refine narrow layouts but cannot be required for legibility. Dark-mode inversion varies by client; never assume the website's dark palette transfers to mail. Test both light and dark client modes and adjust only if evidence warrants it. Gmail documents broad but incomplete CSS/media-query support; a conservative fallback is therefore deliberate, not aesthetic regression ([Gmail CSS support](https://developers.google.com/workspace/gmail/design/css)). WCAG's ordinary text minimum is 4.5:1; the chosen ink, secondary copy, and CTA combination clear that threshold by local contrast calculation, but real-client rendering still needs inspection ([W3C contrast guidance](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)).

## Editorial language and bilingual behavior

- The identity is **Atelier** throughout. Choose one recurring label: `工坊更新 / Atelier updates` in the subscription promise and update footer; `邮件室 / Mailroom` is an eyebrow, not the sender name. Avoid alternating “notification,” “newsletter,” and “broadcast” in user-facing copy.
- Confirmation follows the selected subscription locale (`zh` or `en`) as its primary language. Include a short companion line in the other language only if it aids recognition; do not duplicate the entire message. Mark genuinely English passages with `lang="en"` in HTML. The English and Chinese action labels must mean the same thing.
- Updates can serve the current mixed-language list with a Chinese primary editorial paragraph and a concise, substantively equivalent English recap. Do not send an English-only subscriber a message whose sole meaningful description is Chinese. If per-recipient localization is later supported, it can replace the companion recap without changing the content contract.
- Subject is a useful content title, not `Atelier 更新通知` alone; recommended pattern: `Atelier｜{actual title}` with a short English descriptor when needed. The preview/opening line should say what was published, not repeat brand or deployment machinery. Keep one title, one 1–3 sentence summary, and one action. No invented release cadence, no pressure language, no “you must click” unless strictly true.
- Confirmation says: a request was made, the recipient may confirm, and an unrequested message can be ignored. The 24-hour expiry in the current system may be stated accurately. Update footer says why the recipient got the email and offers **Unsubscribe / 退订**. Do not say “because you confirmed” for a recipient whose status has not been verified at send time; the dispatch contract already rechecks this.

## Editable update authoring contract

The checked-in `notifications/*.json` manifest remains the operator's explicit send control (`id`, `subject`, `html_file`, `send`); `send:false` is the drafting state and `send:true` is the reviewed snapshot. Existing queued/sent IDs are immutable. For **new** issues, use the explicit `atelier-fragment-v1` format with an editable HTML body fragment and a required sibling `text_file`; the shared Rust shell supplies the branded document frame and invariant footer. The [template architecture](email-template-architecture.md) defines that implementation contract. Omitted `format`/legacy `document` remains a supported, unchanged full-HTML input, including its required unsubscribe placeholder. A new issue should be authored as one coherent piece, not an arbitrary full-page redesign:

1. Actual canonical article/work URL and title, checked against the published site; no generic homepage button as the primary action.
2. One specific summary explaining why this item is worth opening, with useful English recap when the audience is mixed.
3. The **rendered** message has the shared header, top rule, typography, CTA style, and footer from this spec. The fragment contains only issue-specific title, summary, primary CTA, and optional subordinate context; it does not duplicate the document root, frame, or footer.
4. The `atelier-fragment-v1` fragment contains **no** `{{unsubscribe_url}}`: the shared shell adds exactly one human-readable footer link with that placeholder in a quoted `href`. The sibling text file likewise contains substantive issue content, **not** the unsubscribe placeholder or boilerplate footer; the Worker appends the fixed subscription-reason and unsubscribe footer. Legacy complete HTML documents keep their existing placeholder contract. Preserve the existing `List-Unsubscribe` and one-click headers; the in-message link is complementary, not a substitute.
5. No recipient PII, tracking pixel, hidden copy, remote font, JavaScript, form, or attachment. HTML is trusted-admin-authored in the current Worker and is not sanitized; never interpolate subscriber input into it ([domain validation](../worker/src/domain.rs)).
6. The **rendered** plain-text part includes the actual title, summary, direct content URL, subscription reason, and unsubscribe URL. The authored sibling `.txt` supplies the first three; the fixed footer supplies the last two. The current `worker/src/mail.rs` fallback contains only subject/read link/unsubscribe; it remains a compatibility fallback for legacy campaigns, not a sufficient experience for new issues. Both MIME parts must agree on purpose and destination.

The confirmation mail uses the same frame, but its content and footer are transactional: no update summary, no unsubscribe action before consent, and no one-click unsubscribe headers. It must retain the server-generated HTTPS confirmation URL and an understandable unstyled/raw-URL fallback. Avoid reusing publication-update copy on the confirmation path.

## Acceptance and release guardrails

1. Side-by-side screenshots of the home subscription card, confirmation mail, update mail, and confirmation/unsubscribe action pages show recognizable paper/ink/vermilion identity and the same labels, **without any change to existing public page layout or theme**. Previously sent mail need not and cannot change.
2. Confirmation mail in both locale paths contains brand, clear purpose, correct localized action, ignore/expiry note, valid visible/linkable HTTPS URL, and meaningful plain text. Opening or GET does not confirm; POST does. Current anti-prefetch consent semantics remain intact.
3. A new `atelier-fragment-v1` update draft names one actually published article or work, summarizes it in both audience languages, and points its primary CTA to that canonical item. Its fragment and authored text file contain no unsubscribe token placeholder; the rendered HTML has exactly one footer unsubscribe link, the rendered plain text has its fixed unsubscribe line, and update headers remain intact. `send:false` remains non-sending; only explicitly reviewed `send:true` queues. Legacy full HTML remains valid without silent rewrapping.
4. At 320 px, 600 px, and desktop widths, with images disabled, CSS partially stripped, and light/dark client modes, no critical content vanishes, CTA text remains visible, links remain identifiable, and no horizontal scrolling is needed. Test actual received messages in at least Gmail web/mobile and an Outlook variant rather than treating browser rendering as proof. This is a release QA target, not a claim already verified.
5. Text/link/CTA contrast meets ordinary-text WCAG AA where applicable; focus and screen-reader reading order on action pages remain usable; footer unsubscribe is not hidden by low contrast or tiny text.
6. No live list-wide dispatch or re-send is needed to validate presentation. Preview local/static HTML and send only to owner-controlled addresses after explicit consent. A failed compatibility check blocks a new campaign but not publication of the website itself.

**What would revise this design:** a real received-client test showing the restrained card fails in a major client, or subscriber feedback that the bilingual recap is confusing. Adjust rendering first; do not add a newsletter platform or analytics infrastructure solely for styling. Research on automated visual-failure detection is promising but not a substitute for a small real-client matrix for this low-volume service ([Nighthawk](https://arxiv.org/abs/2205.13945)).
