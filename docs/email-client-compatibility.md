# Atelier email-client compatibility: evidence and design constraints

Status: investigated 2026-09-26. This is implementation guidance, not a claim that the current message has been visually tested in recipient clients. For transport/identity see [Cloudflare mail architecture](cloudflare-worker-mail-architecture.md) and [bounce identity](cloudflare-email-bounce-identity.md).

## Decision

Use **one small, text-first Atelier email shell** for both opt-in confirmation and publication updates. The visual hierarchy can echo the site's colors and editorial typography, but the email must be self-contained: simple tables for page-width/background/container, inline colors and spacing on cells and links, readable system-font stack, no required external image or CSS, a real text link/CTA, and a meaningful `text/plain` alternative. Do not copy the website's CSS/grid into mail. Ship with actual received-message checks in classic Outlook (if available), Outlook web, Gmail web/mobile, and iOS/Apple Mail before broad dispatch. The HTML is a progressive enhancement, not the sole source of information.

| Concern | Evidence and strength | Practical implication |
| --- | --- | --- |
| Inline CSS and structure | Gmail's [official CSS guide](https://developers.google.com/workspace/gmail/design/css) explicitly supports embedded `<style>` and many media queries, so “Gmail strips all CSS” is false. However Gmail may ignore unsupported properties/selectors. [Mailchimp's production guidance](https://mailchimp.com/help/css-in-html-email/) recommends basic inline CSS for cross-client reliability, including a 100%-wide table for page background. [Microsoft documents](https://learn.microsoft.com/en-us/troubleshoot/outlook/user-interface/formatting-lost-when-editing-the-htmlbody-property) Outlook's Word HTML processing, which can change CSS formatting; this article concerns messages edited/sent through Outlook, not proof that all incoming HTML is changed identically. | Put essential visual styles inline, on table cells and anchors. A tiny `<style>` block may enhance mobile, never carry essential meaning or the only working layout. Avoid website grid/flex dependency and `<main>` as layout anchor. |
| Tables vs modern layout | [Mailchimp's documented compatibility matrix](https://mailchimp.com/help/limitations-of-html-email/) lists static table layouts, simple inline CSS and web-safe fonts as safe, custom fonts and embedded CSS as caution, JavaScript/forms as unsupported. This is vendor operational guidance, not a formal standards guarantee. | A single-column 100% outer table with a fluid inner table (maximum ~600 px) is enough. No deeply nested layout tables unless a measured client defect requires them. Use semantic headings and paragraphs inside cells; tables are layout scaffolding, not content semantics. |
| Dark mode | [Mailchimp's client-by-client dark-mode guide](https://mailchimp.com/help/design-emails-dark-mode/) reports no-change, partial inversion, and full inversion behavior across clients. It says CSS targeting is inconsistent; [Litmus's 2025 test matrix](https://www.litmus.com/blog/the-ultimate-guide-to-dark-mode-for-email-marketers) gives corroborating client-specific observations. The exact matrix can become stale with client updates. | Ensure foreground/background contrast even after inversion. Prefer solid-fill CTA with explicit text color, underlined links, and transparent/outlined logos. Treat `prefers-color-scheme` as optional enhancement, not a correctness condition. Test actual light/dark modes. |
| Images | [Gmail Help](https://support.google.com/mail/answer/145919?hl=en) says external images can be disabled or withheld for suspicious mail. [RFC 2392](https://www.rfc-editor.org/rfc/rfc2392.html) standardizes `cid:` references to MIME body parts, but it does **not** guarantee consistent presentation in all clients. [Mailchimp](https://mailchimp.com/help/image-requirements-for-templates/) recommends alt text for inaccessible/unloaded images. | Do not use a logo/banner as the only brand label, headline, or action. For optional artwork, use absolute public HTTPS `<img>` with size and alt text; make the message fully intelligible with images off. CID requires multipart packaging and specific client tests, so do not add it merely to make a text-first confirmation look polished. Avoid base64 data URLs and background images as essential content. |
| Buttons and fonts | Mailchimp's [HTML limitations](https://mailchimp.com/help/limitations-of-html-email/) classifies web-safe fonts as safe and custom fonts as caution; its [dark-mode guide](https://mailchimp.com/help/design-emails-dark-mode/) recommends solid-fill buttons and underlined links because colors can invert. | Render CTA as ordinary `<a href>` with substantial cell/anchor padding and conspicuous text; fallback is still a clickable link if styling disappears. Use Arial/Helvetica/system sans for body and optional serif fallback for editorial title; do not depend on remotely loaded web fonts. Keep URL visible in plain text. |
| Plain text | [RFC 2046 §5.1.4](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.4) defines `multipart/alternative` for representations of the **same information**, with the plainest first. | Confirmation text should contain purpose, action URL, expiry/ignore notice if HTML does. Update text should summarize the actual publication, not only repeat subject plus generic “Read the update”; preserve canonical article URL and unsubscribe URL. Test both MIME parts from a delivered message. |

## Local evidence and concrete risks

* `worker/src/mail.rs::confirmation_content` currently emits three bare `<p>` elements and an unstyled link, whereas `notifications/atelier-update.html` and `notifications/atelier-worker-launch.html` use complete documents, different backgrounds/colors, and different editorial treatments. This directly explains the user's style-consistency complaint at source level. It does not establish how the school mailbox rendered the message.
* Both checked-in campaign examples rely on body CSS plus a `<main style="max-width:600px">` container rather than an email-safe table shell. Gmail may render them acceptably; classic Outlook/mobile behavior remains untested. One sample (`atelier-update.html`) is intentionally generic draft content and must not be queued as a real publication announcement.
* `worker/src/mail.rs::update_text` currently reduces the entire HTML campaign to subject, first site link, and unsubscribe link. That is not information-equivalent when HTML contains substantive update copy; improvement is not merely cosmetic.
* The subscription form promises a new-article/work email from `atelier@moesegfault.dev`. A confirmation email should use the same Atelier visual identity while remaining visibly a **consent action**, not imply the subscription is active. Keep the existing POST-only confirmation and unsubscribe semantics; styling must not change them.

## Minimum verification matrix

Check delivered MIME (not just browser preview): 1) images blocked; 2) light and dark mode; 3) narrow viewport; 4) long Chinese and English lines/URLs; 5) keyboard/touch activation of the CTA; 6) `text/plain` complete and corresponding to HTML; 7) confirmation and unsubscribe URLs unchanged and never exposed in screenshots/logs. Sample Outlook Classic separately from New Outlook/web if available; their rendering paths differ. A Chromium screenshot is useful for basic geometry but cannot prove mailbox compatibility.
