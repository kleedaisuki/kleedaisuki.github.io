# Cloudflare Workers migration and opt-in update mail

Status: implemented architecture and operational limits, updated 2026-09-26. This complements [`atelier-architecture.md`](atelier-architecture.md); observations are in [`cloudflare-validation.md`](cloudflare-validation.md), and release operations are in [`cloudflare-deployment.md`](cloudflare-deployment.md). GitHub Actions deployment, canonical-domain DNS cutover, remote D1, one confirmed Outlook subscriber, and receipt of a confirmation message at one **Cloudflare-unverified** school destination are established. General inbox placement, account Billing UI status, and mail delivery across arbitrary domains remain unproven.

## Delivery and compatibility contracts

Astro 5 retains static-site generation (SSG) for complete `zh`/`en` HTML, Blog/Articrafts URLs, RSS, sitemap, `llms.txt`, canonical/hreflang, and the existing CSS theme/layout. Frontend enhancement is TypeScript; no JavaScript is needed to read indexed content. The Rust/Wasm Worker owns only `/api/*`. Root [`wrangler.jsonc`](../wrangler.jsonc) publishes `dist/` as Cloudflare Static Assets, uses `run_worker_first: ["/api/*"]`, `html_handling: "auto-trailing-slash"`, and `not_found_handling: "404-page"`. An unknown article remains a real 404, not a crawlable SPA shell. See Cloudflare's [Static Assets](https://developers.cloudflare.com/workers/static-assets/), [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), and [Rust Worker guide](https://developers.cloudflare.com/workers/languages/rust/).

```text
GitHub Actions → tests → Astro SSG dist/ + worker-build Rust/Wasm → Wrangler deploy
                                                             │
Cloudflare Worker Route: atelier.moesegfault.dev/* (active after completed DNS proxy cutover)
  static paths → pre-rendered assets; /api/* → Rust Worker → D1 + Email Sending
                                          scheduled */5 min → bounded mail dispatch
```

The Worker Route is deployed and the existing CNAME to `kleedaisuki.github.io` is now **proxied**, so sampled canonical-host requests reach the Worker. [Manual cutover Action 36133244601](https://github.com/kleedaisuki/kleedaisuki.github.io/actions/runs/36133244601) changed only that flag; setting it back to DNS-only remains the GitHub Pages rollback path. This is a [Workers Route](https://developers.cloudflare.com/workers/configuration/routing/routes/), not a Custom Domain replacing the CNAME. The preview remains `https://atelier-moesegfault.moesegfault.workers.dev`. Current validation found 798 assets, 23.81 MiB total, with largest 2.65 MiB; Cloudflare's [asset limits](https://developers.cloudflare.com/workers/platform/limits/) still require future growth checks. Preview and sampled canonical read/search routes and 404 were tested, not global DNS propagation; see the validation record.

## Email provider fit: decision and remaining evidence

The chosen transport is **Cloudflare Email Service Email Sending**, sender `atelier@moesegfault.dev`, via the native `EMAIL` binding in [`worker/src/mail.rs`](../worker/src/mail.rs). The sending domain is enabled. The implementation sends one recipient at a time with HTML and a generated plain-text alternative, and attaches `List-Unsubscribe`, `List-Unsubscribe-Post`, and `List-Id` to update mail (not confirmation mail). Cloudflare documents [sending setup](https://developers.cloudflare.com/email-service/get-started/send-emails/), the [Workers binding API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), and [allowed headers](https://developers.cloudflare.com/email-service/reference/headers/). On 2026-09-26, an owner-controlled school destination **absent from Cloudflare Email Routing verified destinations** received a confirmation email in its inbox; a matching `emailSendingAdaptive` event was `delivered` without error. Cloudflare defines `delivered` as acceptance by the recipient server, not inbox placement ([Email logs](https://developers.cloudflare.com/email-service/observability/logs/), [Email lifecycle](https://developers.cloudflare.com/email-service/concepts/email-lifecycle/)). The owner's report adds inbox placement for **this one address only**; message HTML rendering and headers were not inspected. A read-only limits check showed `usage.sent=1` of `quota=1000/day`, versus `usage.sent=0` after the earlier verified-destination test. That agrees with Cloudflare's [pricing rule](https://developers.cloudflare.com/email-service/platform/pricing/) that verified sends do not consume quota and arbitrary-recipient sending requires Workers Paid. The result is strong functional evidence for this address, but Billing UI plan status and broad deliverability remain unchecked.

The product is explicitly requested, double-opt-in **site-update notifications**, not an advertising list. Cloudflare names notifications/alerts as an Email Service use case, while its [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) says it is intended for transactional mail and does not yet provide marketing/bulk tooling. Gmail classifies some update lists as [subscription messages](https://support.google.com/mail/answer/15263077?hl=en). These labels overlap; a consented notification is not automatically forbidden just because one-to-many, but eligibility for this exact recurring update list has not been explicitly confirmed. Treat that as operational/policy uncertainty, not proof that the user's use case is marketing. If Cloudflare disallows it or limits prove unsuitable, retain Rust/D1 consent and campaign state and replace only the mail adapter with a provider explicitly supporting lists, such as [Resend Broadcasts](https://resend.com/docs/dashboard/broadcasts/introduction). Do not silently send mail contrary to provider terms.

### Read-only live Email Service readiness audit (2026-09-25)

This historical audit used the locally authenticated Wrangler 4.140.0 account, read-only Cloudflare API calls, and public DNS lookups. **The audit itself** did not send email, read secret values into logs, or establish delivery; subsequent tests did, as recorded below. It is a point-in-time operational observation, not a guarantee that entitlements or quotas remain unchanged.

| Check | Observation and inference |
| --- | --- |
| Sending domain and DNS | `wrangler email sending list moesegfault.dev` and `settings moesegfault.dev` report Email Sending **enabled** on the apex domain. `wrangler email sending dns get` reports Cloudflare bounce MX, SPF, DKIM, and `_dmarc` records; separate public `Resolve-DnsName` lookups found all four record types (three bounce MX, one SPF TXT, one DKIM TXT, one DMARC TXT). This supports domain onboarding, but does not prove receiving providers will accept a message. |
| Deployed binding | `wrangler deployments list` followed by `wrangler versions view` on the then-current deployed version showed `env.EMAIL (unrestricted)` as a **Send Email** binding. The repository configuration likewise declares `send_email: [{name: "EMAIL"}]` without sender/recipient allowlists. The Rust adapter fixes the sender to `atelier@moesegfault.dev`. Cloudflare says a sender must belong to an onboarded domain; that rule was met by construction, though this configuration audit alone did not test send acceptance ([binding restrictions](https://developers.cloudflare.com/email-service/configuration/send-bindings/)). |
| Quota | Read-only `GET /accounts/{account_id}/email/sending/limits` returned `quota.value=1000`, `quota.unit=day`, `usage.sent=0`, `usage.over_quota=false` at audit time. This is the account's reported **daily** limit, not a monthly allowance or a tested delivery rate. Cloudflare says new-account daily limits can change with reputation ([limits](https://developers.cloudflare.com/email-service/platform/limits/)). |
| Workers plan | Read-only `GET /accounts/{account_id}/workers/account-settings` returned `default_usage_model=standard`. Cloudflare associates Standard with Workers Paid, so this is **supporting evidence**, not billing proof ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). The direct subscriptions API returned HTTP 403 because the local OAuth token lacks Billing Read; the actual subscription state was not independently confirmed. Cloudflare requires Workers Paid for sending to arbitrary recipients ([Email pricing](https://developers.cloudflare.com/email-service/platform/pricing/)). |
| Allowed recipient type | Cloudflare's [limits page](https://developers.cloudflare.com/email-service/platform/limits/) says an onboarded sending domain can send to any recipient immediately; the [binding configuration page](https://developers.cloudflare.com/email-service/configuration/send-bindings/) describes an unrestricted binding differently. At audit time, this documentation mismatch and absence of a test send left arbitrary-recipient acceptance unestablished. The subsequent unverified-destination test below resolves that empirical question for **one address**, not the broader policy/plan interpretation. |

**Post-audit evidence and remaining gate:** As recorded in [live validation](cloudflare-validation.md#owned-mailbox-consent-and-notification-attempt), an owner-controlled **Cloudflare-verified** Outlook mailbox completed subscription/confirmation and received one scheduled HTML update in spam. A later [unverified school-destination test](cloudflare-validation.md#cloudflare-unverified-school-destination-confirmation-test-2026-09-26) established receipt of a confirmation message in that owner's inbox, one `delivered` GraphQL event, and quota usage increasing from zero to one of 1000/day. The school address was not confirmed or sent an update and its pending row was removed. This resolves whether **one ordinary unverified destination** can receive mail, not general inbox placement, policy eligibility, or Billing UI plan state. Confirm Workers Paid in Billing UI (or with Billing Read); inspect delivered plain text, DKIM/SPF/DMARC results, one-click headers, production unsubscribe POST, and cross-domain performance before relying on broader campaigns. Cloudflare [exempts verified destinations from quota](https://developers.cloudflare.com/email-service/platform/pricing/), explaining the earlier zero-usage observation.

## Implemented data model and consent flow

[`worker/migrations/0001_init.sql`](../worker/migrations/0001_init.sql) is the authoritative schema; the earlier illustrative schema is superseded. Times are Unix milliseconds. D1 uses prepared, bound statements; grouped enqueue uses `batch()` ([D1 Worker API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [migrations](https://developers.cloudflare.com/d1/reference/migrations/)).

| State owner | Current invariant and implementation |
| --- | --- |
| Git + Astro | Published HTML and canonical content do not depend on D1 or mail availability. |
| `subscribers` | `pending`, `confirmed`, `unsubscribed`; locale is `zh` or `en`. Dispatch selects only confirmed recipients and rechecks consent just before each send. An opted-out address needs a fresh confirmation to reactivate. |
| Confirmation token | A 256-bit random token is mailed; only its SHA-256 hash is in D1. It expires after 24 hours. GET shows a `noindex` action page without consenting; POST atomically consumes it. |
| Unsubscribe token | A distinct 256-bit opaque token is stored **raw** in D1, inserted into the recipient's HTTPS link, and accepted by POST for browser or RFC 8058 one-click opt-out. GET only shows a form, protecting against link prefetch. Raw storage is an implementation choice, **not technically necessary** for direct links: hashing the submitted token would also permit lookup. A D1 read leak could permit unauthorized opt-outs; revisit this trade-off before broad use. Never log, expose, or index tokens. |
| `campaigns` | Stable CI-supplied `id`; editable `draft` with subject and trusted-admin HTML. `send:true` snapshots current confirmed subscribers and freezes the campaign as `queued`. Same content is idempotent; changing a queued/complete campaign conflicts. `complete` requires all deliveries to be `sent` or `skipped`. |
| `deliveries` | Per-campaign, per-email: `pending`, `sending`, `sent`, `failed`, `unknown`, `skipped`. An atomic claim acquires a lease. An expired `sending` lease becomes `unknown`, **not** automatically retryable, because provider acceptance may have preceded a Worker/D1 failure. |

`POST /api/subscribe` accepts bounded JSON or native form data, applies the `SUBSCRIBE_LIMIT` Cloudflare rate limiter (10 requests per 60 seconds per hashed source IP), rejects cross-origin browser forms, and returns non-enumerating success for existing confirmed/pending addresses. The service conservatively accepts ASCII dot-atom email and lowercases the entire address for identity; that can merge theoretically case-sensitive local parts and excludes SMTPUTF8, a documented product constraint in [`worker/src/domain.rs`](../worker/src/domain.rs). An unsubscribed address moves to `pending` on a fresh request; only the confirmation POST regains `confirmed`. Explicit confirmation-send failure expires the pending token to permit a retry. API responses use `no-store`, `noindex`, and `no-referrer`. Revisit abuse protection if automated sign-ups appear; client-only CAPTCHA is not a control ([Turnstile server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)).

## Editable CI campaign and bounded dispatch

The public frontend never receives mail/admin credentials. [`notifications/atelier-update.json`](../notifications/atelier-update.json) is a draft example; a sibling editable HTML file contains the message and mandatory `{{unsubscribe_url}}` link. The manifest declares stable `id`, `subject`, `html_file`, and `send`, defaulting to `false`. A `main` push deploys code/assets first, then [`scripts/dispatch-notifications.mjs`](../scripts/dispatch-notifications.mjs) submits **only changed manifests or manifests whose referenced HTML changed** to authenticated `POST /api/admin/notify`. A changed manifest with `send:false` updates a draft without mailing anyone. Deliberately set `send:true` only after reviewing the published destination and exact HTML. The endpoint validates bounded subject/HTML and snapshots recipients when queuing; `GET /api/admin/status?id=...` returns counts without addresses. A manual workflow dispatch and ordinary content-only pushes do not automatically send mail. CI setup is in the deployment runbook.

The scheduled handler runs every five minutes and claims at most 20 deliveries, one at a time. Explicit rate-limit rejection waits 15 minutes; daily-limit rejection waits 25 hours. Rate, daily, and configuration rejections also defer the rest of that campaign rather than hammering the provider. Configuration errors—including recipient-not-allowed, validation, sender and header errors—retry after an hour; explicit recipient suppression/delivery failure becomes `skipped`. Ambiguous errors and expired leases become `unknown` for manual reconciliation. Explicit retry is capped at five attempts. Cloudflare's [rate/limit behavior](https://developers.cloudflare.com/email-service/platform/limits/) informs these local policy delays; they are not provider guarantees. [`worker/src/lib.rs`](../worker/src/lib.rs) and [`worker/src/store.rs`](../worker/src/store.rs) are the source of truth. Neither the native binding nor D1 makes dispatch exactly once; blindly retrying `unknown` can duplicate messages. The admin status endpoint is the current inspection tool; provider event/message-ID reconciliation and bounce/complaint suppression are not implemented. Cloudflare offers [Email Sending event subscriptions](https://developers.cloudflare.com/email-service/platform/event-subscriptions/) if volume warrants them.
